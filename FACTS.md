# agentdispatcher — Project Facts

## 📌 Pinned rules
_Explicit user instructions — always apply these. When a rule shapes your action, say so briefly (e.g. “per pinned rule ‘…’”)._
- **cost_provenance_and_no_double_counting**: Maintain one tenant-scoped ledger with stable source/event/request IDs and parent-child execution links. SDK, OTel and gateway records for the same attempt are correlated, not counted as extra charges; genuine billed retries/fallbacks remain distinct. Parent job/MCP totals roll up unique child charges plus separately evidenced tool fees. Distinguish provider-reported/billed, rate-calculated, subscription fees and estimated API-equivalent value; never sum subscription equivalent value as actual extra spend. Unknown cost/coverage is not zero. Use decimal money with currency, rate/config provenance, requested and served provider/model, and reconciliation evidence. All tenant authorisation comes from validated credentials/membership.
- **yaml_configuration_optimisation**: Manage authorised application YAML using reusable repository, app API and local connector adapters. Preserve YAML as authoritative app configuration, record redacted versions/diffs/audits in tenant-scoped PostgreSQL and correlate runtime usage with the effective prompt/config version. Suggest cheaper compatible models using permitted or synthetic workload evaluations of quality, latency, reliability and total successful-task cost. Show changes, enforce write grants, validate schema/capabilities and source revision, preserve unrelated content, verify runtime activation and support rollback. Read permission does not grant write permission; lower token price alone does not establish equivalent quality. Record optimisation/evaluation cost separately.
- **react_monitoring_and_embedded_sdk**: React is primarily the responsive desktop/mobile monitoring interface, not the app-execution agent. Use a small reusable OpenTelemetry-based integration inside consuming apps at their shared LLM client and scheduler/job entrypoints; it requires no LLM for monitoring. AgentTrade plus one scheduled job is the first integration. Propagate job/run/step/request/trace and config version through asynchronous workers and MCP services; distinguish executing service from beneficiary tenant/user. Instrument internal MCP LLM work explicitly. Capture lifecycle, heartbeat and coverage with bounded non-blocking export, deduplication and visible loss. Gateway controls apply only to routed traffic; CLI/web telemetry coverage is capability-dependent. Electron is optional later, not the primary UI.
- **open_source_easy_install_and_credits**: AgentDispatcher is intended for public Apache-2.0 open-source distribution. Keep dependencies and custom code minimal; reuse suitable open-source components while preserving attribution and license obligations. Supply a clean-checkout Docker Compose quickstart, documented env example, offline deterministic demo requiring no provider key, separate live-provider smoke instructions and concise testing/contributing docs. Maintain LICENSE, THIRD_PARTY_NOTICES.md, required upstream license texts, README Built on, in-app licenses and dependency/license checks for shipped components/assets/images. No LiteLLM enterprise code or mandatory prohibited AGPL/commercial dependencies; OpenRouter is optional. Pin reviewed supported releases and verify advisories at implementation/release rather than relying on old minimum-version claims.
- **independent_services_single_monorepo**: Use one Git monorepo with real independently deployable services: responsive React/TypeScript UI, Python/FastAPI Dispatcher API, dedicated background worker/scheduler, LiteLLM gateway and OTel collector, backed by PostgreSQL. Each service has its own entrypoint/container, configuration, health check and restart lifecycle. Share focused packages/contracts; no copied domain logic or imports into another service's internals. One migration owner controls application schema. Default Compose install uses PostgreSQL-backed background coordination and needs no Kubernetes, Redis or external broker. Monitor external app schedulers without taking over their business scheduling.
- **postgresql_tenant_data**: PostgreSQL is the authoritative store for all durable AgentDispatcher product data: tenant/app identities, usage/price records, jobs/runs/traces, policies, configuration snapshots, evaluations and audit/history. Every tenant-owned record, query, join, worker and export must preserve authenticated tenant scope; enforce RLS with non-bypass runtime roles and tenant-aware constraints. Minimal default is one PostgreSQL cluster with tenant-isolated shared application schema, not one database per tenant; physical per-tenant databases are an optional later deployment choice. Separate LiteLLM-owned storage/roles. App YAML remains its source; version snapshots/history live in PostgreSQL. Secrets stay in encrypted secret storage/env; SDK spools are bounded transient transport buffers. Test at least two tenants and pooled connections. Telemetry tags are attribution, never authentication.
- **reusable_minimal_code**: Write once, reuse many: keep AgentDispatcher minimal with single-purpose classes, short well-named methods/functions and shared modules as the single source of each behaviour. Prefer composition and clear data flow; no duplicated pricing, attribution, validation or connector logic, speculative abstractions or silent failures. Add short public docstrings explaining purpose and non-obvious constraints; comments explain why. Match surrounding style, remove dead code, validate boundaries, configure URLs/ports/paths/limits through env/config and keep secrets out of source. SQL is named _SQL_* constants at file top with parameterised queries; migrations are appended and idempotent. Use focused tests for meaningful behaviour.
